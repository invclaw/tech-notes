> [!FOCUS] 强隔离派的核心诉求
> 如果你要做一个**面向公网的多租户 Agent 平台**，或者用户本机不想/不能装 Docker，却要放手让 Agent 执行任意安装、编译、爬虫和不可信脚本——**硬件虚拟化级别的轻量虚拟机（MicroVM）与云端一次性沙箱**就是终极防线。

## 1. 轻量虚拟机（MicroVM）的底层原理

以 **Firecracker**（AWS Lambda / E2B / Fly.io 底座）、**Cloud Hypervisor** 与 macOS **Apple Virtualization.framework** 为代表，MicroVM 打破了“虚拟机一定又慢又笨重”的旧印象：

1. **硬件级独立内核**：依托 CPU 硬件虚拟化扩展（Intel VT-x / AMD-V / Apple Silicon），每个沙箱运行**完全独立的 Guest Linux 内核**。哪怕沙箱内拿到 root 权限甚至把 Guest 内核打崩，也影响不到宿主机和其他租户。
2. **为什么能做到百毫秒级启动？**
   - **极简设备模型**：彻底砍掉传统 QEMU 里复杂的 BIOS、USB、显卡、老旧 PCI 模拟，只保留极少数精简的 `virtio` 设备（块存储、网卡、串口/vsock），启动链路极短；
   - **内存快照恢复（Snapshot Restore）**：云端沙箱平台（如 E2B、Modal）会预先把装好 Python/Node 环境的 MicroVM 启动好并拍成内存快照；新请求到来时直接把内存页按需映射恢复出来，跳过整个 OS 引导过程，实现百毫秒级“秒醒”。

## 2. 云端托管沙箱的三大架构难题

把沙箱搬到云端（如 E2B、Daytona、OpenClaw 的 Crabbox / OpenShell）后，隔离问题解决了，但会引入三个新的工程挑战：

1. **工作区谁是真源？（本地 vs 云端同步）**
   - **Mirror 双向同步模式**（如 OpenShell `mirror`）：本地保持真源，每次执行前把改动推上云、执行完再拉回本地。体验最像本机，但每次执行都有同步延迟且需要防本地编辑器并发写冲突；
   - **Remote 远端真源模式**（如 SSH / Crabbox / E2B）：首次初始化时把代码树原子上传一次，后续编辑、构建、Git 操作全在云端完成，最后只把结果或 PR 推回，吞吐高、延迟低。
2. **租约与成本防失控**：
   - 必须为每个作用域预留**固定租约 ID**（防网络抖动重试时重复开出多台僵尸云机器）；
   - 必须同时设置 **总生存期（TTL）** 与 **空闲休眠超时（Idle Timeout）**，先到者生效，并确保凭据只留在控制面宿主机、不自动灌进云机器环境变量。
3. **跨网交互体验**：
   - 命令流式输出、PTY 交互终端、文件浏览与端口预览都需要通过控制面隧道（SSH / vsock / HTTPS 代理）转发，延迟天然高于本机进程。

## 3. 实战选型决策指南

不同业务形态下，应该直接对号入座，而不是盲目追求“最重”或“最轻”：

| 你的业务场景 | 推荐沙箱层级 | 典型选型 | 核心理由 |
|---|---|---|---|
| **单人本机 Coding Assistant** | **L2 · OS 进程级** | macOS Seatbelt / Linux `bwrap` + Landlock（Codex / Claude Code 路线） | 毫秒级启动、零镜像维护、直接复用本机全套编译器和依赖 |
| **个人 / 小团队 7×24 多渠道 AI 控制面** | **L3 · 标准容器级** | Docker / Podman + 断网/只读根/剥离能力（OpenClaw 默认路线） | 跨平台一致、可隔离群聊与访客、支持独立沙箱浏览器、本机零云费用 |
| **本机不想装 Docker，但控制面留本地** | **L5 · 云端租约机** | Crabbox（Daytona）/ OpenShell 远端 | 控制面与凭据留本机，不可信执行全甩给用完即弃的云机器 |
| **公网多租户 Agent SaaS 平台** | **L4 强化容器 / L5 MicroVM** | Firecracker（E2B / Modal）或 Kata / gVisor | 面对完全不可信的陌生用户代码，必须守住内核级硬隔离底线 |
| **纯脚本 / 数据处理 / 插件扩展** | **L1 · 语言运行时** | WASM / QuickJS / V8 Isolate | 微秒级启动、极低内存、能力白名单精确可控 |
