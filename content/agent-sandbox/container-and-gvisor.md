> [!FOCUS] 均衡派的核心诉求
> 当 Agent 不再只是“本机帮个人写代码”，而是要**7×24 常驻、接多个聊天渠道、甚至服务陌生人或团队访客**时，进程级沙箱的跨平台差异和宿主机耦合就会成为隐患。**容器与强化容器**在隔离度、可复现性与启动开销之间取得了最务实的平衡。

## 1. 标准容器沙箱（Docker / Podman）—— OpenClaw 默认底座

容器并不是一台虚拟机，而是宿主机 Linux 内核上的**受限进程组**，靠三套内核机制拼出“独立机器”的错觉：

1. **Namespaces（视野隔离）**：给容器独立的进程树（PID）、挂载视图（Mount）、网络栈（Network）、主机名（UTS）与用户映射（User），让容器里的进程看不到宿主机上的其他进程、文件和网卡。
2. **cgroups v2（资源预算封顶）**：硬性限制容器最多能用多少 CPU、内存、以及最大进程/线程数（`pids.max`），防止模型写出死循环或 Fork 炸弹把宿主机拖死。
3. **最小权限加固（真正决定安全上限的关键）**：
   - 默认只挂容器并不安全！生产级 Agent 容器必须叠加：**默认断网（`network: none`）+ 只读根文件系统 + 限容 `tmpfs` + 丢弃全部 Linux Capabilities（`capDrop: ALL`）+ 禁止提权（`no-new-privileges`）**。

### Docker vs Podman 的小差异
- **Docker** 生态最成熟，但在 Linux 上默认有 root 权限的守护进程（dockerd）；
- **Podman** 采用无守护进程架构，原生支持 **Rootless 模式**（容器引擎本身以普通用户身份运行），进一步缩小一旦逃逸后的宿主机破坏半径。

> [!WARNING] 标准容器的根本边界：共享宿主机内核
> 无论容器外层怎么加固，容器内的所有系统调用最终都直接交给**宿主机的同一个 Linux 内核**处理。对于个人或半信任团队已经足够安全；但如果你要对外开放多租户公网 SaaS、执行完全不可信的第三方恶意代码，一旦命中 Linux 内核 0-day 漏洞，理论上仍存在容器逃逸风险。

## 2. 强化容器：如何堵住“共享内核”的缝隙？

为了在保留容器镜像生态的同时把宿主机内核藏起来，业界发展出两条强化路线：

### 2.1 gVisor（用户态内核拦截）
- **核心原理**：在容器和宿主机 Linux 内核之间插入一个用 Go 编写的**用户态内核（Sentry）**。容器内发出的绝大多数系统调用（文件、网络、信号等）不再直达宿主机内核，而是由 Sentry 在用户态模拟处理，只把极少数经过严格收敛的底层调用转发给宿主机。
- **权衡**：极大压缩了宿主机内核攻击面，启动比传统 VM 快得多，无缝兼容 Docker / Kubernetes 镜像；代价是**高频率系统调用或密集文件 IO 场景下性能明显下降**，且极少数偏门内核特性可能不兼容。

### 2.2 Kata Containers（把每个容器装进轻量 VM）
- **核心原理**：表面上完全遵守 OCI 容器标准（和 Docker / K8s 无缝对接），底层则利用硬件虚拟化（KVM）为每个 Pod/容器拉起一个独立的极简 Linux 内核。
- **权衡**：隔离强度直接跃升到虚拟机级别，且 100% 兼容真实 Linux 内核行为；代价是宿主机必须支持硬件虚拟化（嵌套虚拟化的云服务器往往受限），且每个容器的内存底噪比普通容器更高。
