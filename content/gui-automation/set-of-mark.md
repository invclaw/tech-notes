> [!FOCUS] 为什么要发明 Set-of-Mark（SoM）？
> 多模态大模型虽然能“看懂”网页截图，但**直接让它猜像素坐标（如 `x=734, y=218`）非常容易偏几十像素点歪**；而 **Set-of-Mark（SoM）** 在截屏前先给每个可点击元素画上彩色边框和醒目数字标号（`[1]`、`[2]`、`[3]`），瞬间把困难的**“连续像素坐标回归”**降维成了大模型最擅长的**“离散数字选择题”**（输出 `click(3)`）。

## 1. 截图标号到底是怎么实现的？（完整 5 步拆解）

以最常见的浏览器场景（如 `browser-use` / Playwright Agent）为例，每一次标号截图背后都执行以下 5 步：

### 第 1 步：找出当前视口里所有“真正可点”的元素（框从哪来？）
有两种框选来源：
- **浏览器 DOM 探针（最准、最快）**：通过 CDP `Runtime.evaluate` 向页面注入一小段探针 JS，遍历可见 DOM（含 Shadow DOM 和 `iframe`），按规则筛选可交互元素：
  - 原生交互标签：`<a>`、`<button>`、`<input>`、`<textarea>`、`<select>`；
  - 语义属性：`role="button"`、`tabindex >= 0`、`contenteditable="true"`；
  - 样式特征：`getComputedStyle(el).cursor === "pointer"`（抓出用 `<div>` 冒充按钮的前端组件）。
- **两道关键过滤（去掉垃圾框）**：
  1. **视口与尺寸过滤**：用 `el.getBoundingClientRect()` 取矩形框，剔除宽高为 0 或滚出当前屏幕的元素；
  2. **遮挡剔除（Occlusion Check）**：对矩形框中心点调用 `document.elementFromPoint(cx, cy)`——如果命中的不是该元素本身或子孙，说明它**被弹窗或吸顶栏盖住了**，直接剔除不打标！
- **无 DOM 场景（Canvas / 桌面软件，如微软 OmniParser）**：拿不到 DOM 时，先跑一个极轻量的本地目标检测模型（如微调的 YOLO）从截图像素里框出所有图标与按钮，再配合 OCR 识别文字。

### 第 2 步：在内存中建立「数字编号 ↔ 真实目标」映射表
按从上到下、从左到右给过滤后的元素编号 `1, 2, 3...`，把映射关系留在 Agent 运行时内存里：
```json
{
  "1": { "tag": "input", "type": "email", "center": [169, 122] },
  "2": { "tag": "input", "type": "password", "center": [169, 172] },
  "3": { "tag": "button", "text": "立即登录", "center": [109, 227] }
}
```

### 第 3 步：把彩色边框和数字标签画出来（两种画法）
- **画法 A：页面 DOM 透明覆盖层（最常见）**
  - 在页面顶层挂载一个 `position: fixed; inset: 0; pointer-events: none; z-index: 2147483647` 的容器，按刚才拿到的每个 `(x, y, w, h)` 画出彩色细边框，并在左上角贴一个高对比度数字小标签（如红底白字 `3`）；
  - 工程细节：相邻按钮太密时做标签避让，防止数字标签盖住旁边按钮的文字。
- **画法 B：离屏图片合成（不碰 DOM）**
  - 先截一张干净的原始图，再在宿主侧用图像处理库（Sharp / Pillow / Canvas）把框和数字画到图片字节上——**完全不改动网页 DOM**，既不会触发某些网站的 DOM Mutation 检测，也更干净。

### 第 4 步：截屏送模型，并立刻清理覆盖层
- 若采用画法 A，调用 CDP `Page.captureScreenshot` 截完带标号的图后，**同一毫秒立刻把覆盖层 DOM 移除**，绝不影响后续真实点击；
- 把**带标号截图**（通常再附带一份简短的编号文字清单）发给多模态模型，模型只需回复：`click(mark_id=3)`。

### 第 5 步：查表还原并执行真实操作
- 运行时用模型返回的 `3` 查第 2 步的映射表，拿到真实元素引用或中心点 `(109, 227)`，调用 Playwright `locator.click()` 或 CDP `Input.dispatchMouseEvent` 精准点击；
- 动作完成后页面发生变化，**旧编号立刻作废**，下一轮重新执行第 1～4 步生成新标号。

## 2. AXTree vs SoM vs 纯视觉坐标：三者怎么选？

| 定位方式 | 发给模型什么 | Token 成本 | 精准度 | 最擅长什么场景 |
|---|---|---|---|---|
| **纯 AXTree（无障碍树）** | 纯文本树 + `ref` 编号 | **最低** | 极高（有语义标签时） | 常规后台、表单、文档、文字按钮 |
| **SoM（视觉标号）** | 带框带数字的截图（+ 简短索引） | 中等（1 张图） | **极高**（解决纯图标/无文本按钮） | **纯图标按钮、视觉布局判断、缺失 ARIA 属性的网页** |
| **纯视觉坐标（Computer Use）** | 原始无标号整屏截图 | 较高（易重试微调） | 中等（易偏像素） | 无法注入 DOM 且未跑检测模型的任意桌面软件 |

> [!TIP] 现代 Browser Use 的最佳组合
> 成熟框架（如 `browser-use`）往往默认采用 **AXTree + SoM 混合**：文本树提供精准语义与控件状态（是否勾选、当前输入值），带标号截图提供空间位置与视觉上下文（哪个按钮在红色报错框旁边），两者共享同一套数字编号，准确率最高。
