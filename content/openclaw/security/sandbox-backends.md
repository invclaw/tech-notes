> 回答三个核心问题：**OpenClaw 默认采用哪种沙箱？它支持哪五种可插拔后端？以及它和 Codex、Claude Code、云端 MicroVM 等其他 Agent 沙箱有什么本质区别？**

## 1. 默认策略：什么进沙箱？默认用哪种沙箱？

先明确两条容易混淆的默认事实：
1. **默认开关是关闭的（`mode: off`）**：单人本机开箱使用时默认不启沙箱，工具直接在宿主机运行以保证零门槛体验；
2. **一旦开启沙箱，默认后端是本地 `Docker` 容器**：无论是按会话开启（如仅隔离群聊/频道、全量隔离）还是由访客角色强制触发，默认都会拉起本地轻量 Linux 容器（默认断网、只读根文件系统、剥离全部内核能力、默认不暴露 Agent 宿主机工作区）。

同时，OpenClaw 坚守**控制面与执行面分离**：
- **进入沙箱执行的部分**：命令行与进程工具（`exec`、`process`）、文件读写与目录浏览工具（`ls`、`read`、`write`、`edit`、`apply_patch`），以及可选的**独立沙箱浏览器容器**；
- **永远留在宿主机的部分**：**Gateway 控制面本身**、会话数据库、模型 API Key、GitHub 托管凭据，以及运行在 Gateway 侧的原生插件与 MCP 服务（沙箱会话调用它们时需额外通过“沙箱工具策略”二次审批）。

## 2. 五大可插拔沙箱后端对比

OpenClaw 没有把沙箱绑死在单一技术上，而是抽象出统一后端接口，内置支持 **5 种后端**：

| 沙箱后端 | 底层载体 / 运行位置 | 工作区同步模式 | 网络与浏览器能力 | 最适合的场景 |
|---|---|---|---|---|
| **1. Docker（默认）** | 本机 Docker 容器（轻量 Debian 镜像） | 宿主机目录绑定挂载（或独立沙箱目录） | 默认彻底断网（`none`）；**唯一支持独立沙箱浏览器容器**；支持额外挂卷与 GPU | 本机开发与绝大多数个人/团队部署的首选 |
| **2. Podman** | 本机 Podman 容器（无守护进程 / Rootless） | 同 Docker，支持挂载与独立目录 | 默认断网 + 限容内存盘；支持 Podman 5+ GPU | 偏好无 Root 守护进程容器引擎的 Linux 环境 |
| **3. SSH 后端** | 任意 SSH 可达的独立远端机器 | **远端为真源**（首次初始化播种一次，后续文件工具走 SSH 桥接） | 取决于远端主机网络策略；不支持沙箱浏览器与本地 bind 挂载 | 把高危命令卸载到一台独立测试机/专用隔离机 |
| **4. OpenShell 后端** | 由 OpenShell 网关（如 NVIDIA OpenShell）托管的本地或远端沙箱（底层可跑容器或虚拟化） | 支持 **Mirror（本地为真源，每次执行前后双向同步）** 或 **Remote（远端为真源）** | 由 OpenShell 策略控制；暂不支持沙箱浏览器 | 企业级托管沙箱网关、统一策略与可选双向同步 |
| **5. Crabbox 后端** | 由 Crabbox 按租约申请的**一次性云端机器**（如 Daytona） | 首次原子上传整棵工作区树到云端，以远端为真源；支持 TTL + 空闲双超时 | 受云端供应商策略控制；不支持沙箱浏览器与本地 bind 挂载 | Gateway 留本机，但本机不想装 Docker，希望工具全跑在用完即弃的云机器上 |

### OpenShell 与 Crabbox 的两个关键设计取舍
- **OpenShell 的 Mirror vs Remote**：`mirror` 模式每次执行前同步本地到沙箱、执行后同步回本地（带进程内互斥锁防并发踩踏），体验接近本机 Docker，代价是每次执行有同步开销；`remote` 模式只播种一次，以远端为准，延迟更低。
- **Crabbox 的固定租约 ID**：申请云机器前先在本地预留固定租约 ID，失败或重启重试时复用同一 ID，避免误开多台“僵尸云机器”；释放时由归属仓库强校验后才销毁。

## 3. 横向对比：OpenClaw 沙箱 vs Codex / Claude Code / 云端 MicroVM

把主流 AI Agent 的沙箱放到同一张架构坐标系里看，其实分属**四条不同的技术路线**：

| 代表项目 | 核心沙箱技术 | 隔离粒度 | 启动速度与依赖 | 核心优势与局限 |
|---|---|---|---|---|
| **OpenClaw** | **容器级默认（Docker / Podman）** + 可插拔远端（SSH / OpenShell / Crabbox） | **完整独立用户态环境**（独立根文件系统、网络栈、进程树） | 百毫秒～秒级；本地需装 Docker/Podman（否则切 Crabbox 云端） | **优势**：跨平台隔离行为一致、默认彻底断网、支持沙箱浏览器、天然适配群聊与多访客隔离；**局限**：比进程级沙箱重，需要维护镜像 |
| **OpenAI Codex** | **OS 原生进程级沙箱**：macOS 用 **Seatbelt**；Linux 用 **Bubblewrap（`bwrap`）+ Landlock / Seccomp**；Windows 用受限令牌 | **单条子进程级**（直接在宿主机内核上给子进程套权限罩，如只读 / 仅工作区可写） | **毫秒级启动、零容器依赖**，直接复用宿主机已装编译器与工具链 | **优势**：极轻极快、无需配镜像、本地写代码体验无缝；**局限**：共享宿主机用户态环境，受宿主机内核策略制约（如 Ubuntu AppArmor 限制非特权命名空间会导致 `bwrap` 失败），不适合多租户长驻隔离 |
| **Claude Code** | **OS 原生进程级沙箱**（同样是 macOS Seatbelt + Linux `bwrap`）+ 域名级网络代理 + 人工审批 | **单条子进程级** + 细粒度出网代理 | **毫秒级启动、零镜像维护** | **优势**：轻快且可做细粒度域名放行；**局限**：同样共享宿主机工具链，定位面向单人本机开发 |
| **云端 MicroVM 沙箱**（如 E2B / Firecracker / Daytona） | **轻量虚拟机（MicroVM）或独立云容器** | **独立内核级（MicroVM）** 或独立云主机 | 秒级开机/唤醒 + 网络往返延迟 | **优势**：隔离强度最高（独立内核，几乎杜绝宿主机逃逸），免本机装容器；**局限**：有网络延迟、文件同步成本与租约费用 |

> [!FOCUS] 为什么 OpenClaw 选了“容器为主”，而不是像 Codex 只用 `bwrap` / Seatbelt？
> **产品定位决定了沙箱选型**：
> - **Codex / Claude Code 面向“单人本机写代码”**，最看重零配置、毫秒级启动和直接复用开发者本机环境，因此 OS 原生进程级沙箱是最优解；
> - **OpenClaw 面向“7×24 常驻、接 20+ 聊天渠道、支持群聊与多人访客的 AI 控制面”**，需要跨平台一致的强隔离、默认彻底断网、支持独立沙箱浏览器以及按访客独立容器，因此选择**容器作为默认底座**，再通过可插拔后端向上兼容云端租约机器（Crabbox）与托管沙箱（OpenShell）。

> [!WARNING] 实战避坑：Docker 容器里套 Codex `bwrap` 的嵌套冲突
> 当 OpenClaw 开启 Docker 沙箱并同时使用本地 Codex 时，容易出现“容器内再套一层 `bwrap`”的嵌套命名空间冲突（Ubuntu/AppArmor 常禁止非特权 User/Network Namespace）。OpenClaw 的安全原则是：**绝不为了迁就嵌套 `bwrap` 而给 Docker 容器提权**，而是将工具执行统一收口到 OpenClaw 自己的沙箱工具，或在宿主机用最小权限 AppArmor 规则放行。
